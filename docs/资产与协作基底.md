## 多角色协作约定（建议）

角色是职责视角，一人可以承担多个角色；AI 可辅助梳理、对比和审阅，不替代真实的业务、飞行、安全及验收责任人。角色讨论应记录依据、分歧和待决事项，不以模拟意见冒充真实专家结论。

| 角色视角 | 主要职责 | 实际负责人 |
| --- | --- | --- |
| 业务决策 / 产品 | 明确目标用户、优先级和 MVP，确认业务取舍 | 待确认 |
| 项目管理 | 跟踪阶段出口、依赖、问题和责任人 | 待确认 |
| 工地安全 / 监理 | 提供现场流程、隐患判断及整改验收规则 | 待确认 |
| 无人机作业 / 设备 | 提供设备能力、接口、作业和安全边界 | 待确认 |
| 数据 / AI | 样本与标注、识别可行性和误报漏报评估 | 待确认 |
| 架构 / 交付 | 评估集成、网络、安全、部署及技术方案 | 待确认 |
| 测试 / 验收 | 核实验收标准、验证条件及实际证据 | 待确认 |

建议一个事项采用“提出人整理依据 → 相关角色提出约束与备选 → 业务或技术责任人决策 → 记录结论和未决项”的方式；涉及多方权限或安全责任的决策由相应负责人参与。参与方和决策权尚未指定，不预设组织架构。

## 工作与文档约定

1. 新资料放入 `assets/` 对应分类，并在资产登记表补充来源、版本、授权范围和用途；无法确认的字段写“待确认”。
2. 使用既有参考资料时区分领导设想、资料陈述、团队建议、已批准决策和验证结果。引用到需求时保留资产编号或具体位置。
3. 需求和架构取舍记录在 [决策与待确认事项](决策与待确认事项.md)；跨阶段状态更新 [项目总纲](../openspec/project-roadmap.md)。
4. 具体功能范围确定后再创建 OpenSpec 变更；评审通过并归档后维护相应系统规格。
5. 禁止把凭据写入仓库；敏感影像和大文件先确认使用范围、存储与版本管理方式。当前已复制的参考文件暂不视为已获准提交或公开。
